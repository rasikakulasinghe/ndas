# NDAS URL Routing & View Contracts

> **Generated by:** BMAD document-project workflow (Step 4 — Exhaustive Scan)
> **Architecture:** Django MTV — all views render HTML templates. No REST/JSON API except specific HTMX endpoints.
> **Auth:** All views require `@login_required(login_url="user-login")` except login/password-reset.
> **Rate Limiting:** `@ratelimit(key='user_or_ip', rate='10/m')` on create/edit, `5/m` on delete.

## Standard View Pattern

All authenticated views follow this structure:

```python
@login_required(login_url="user-login")
@require_http_methods(["GET", "POST"])          # or @require_GET for read-only
@ratelimit(key='user_or_ip', rate='10/m')       # 10/m for create/edit, 5/m for delete
@handle_view_errors(redirect_url='...', error_message='...')
def my_view(request, pk):
    obj = get_object_or_404(MyModel, id=pk)     # NEVER use .objects.get()
    related = Related.objects.filter(parent=obj).select_related('added_by')

    if request.method == 'POST':
        # process form
        pass

    return render(request, "app/template.html", {"obj": obj})
```

## URL Naming Convention

| Pattern | Example | Description |
|---------|---------|-------------|
| `{entity}-manager` | `assessment-manager` | List view, all records |
| `{entity}-manager-{filter}` | `assessment-manager-normal` | Filtered list |
| `{entity}-manager-{scope}` | `assessment-manager-patient` | Records for specific parent |
| `add-{entity}` / `{entity}-add` | `add-patient`, `cdic-assessment-add` | Create form |
| `view-{entity}` / `{entity}-view` | `view-patient`, `cdic-assessment-view` | Detail view |
| `edit-{entity}` / `{entity}-edit` | `edit-patient`, `cdic-assessment-edit` | Edit form |
| `delete-{entity}` / `{entity}-delete` | `delete-patient`, `cdic-assessment-delete` | Delete action |

**URL Namespace Usage:**
- `video` app: use `{% url 'video:manager' %}` in templates
- `reports` app: use `{% url 'reports:builder' %}` in templates
- Other apps: use plain name `{% url 'add-patient' %}`

## Delete Flow (Unified Modal Pattern)

All delete endpoints use the unified delete confirmation modal. The flow:

1. User clicks delete → modal appears (`{% include 'src/partials/delete_confirmation_modal.html' %}`)
2. User confirms → `POST` to delete URL
3. View calls `has_delete_permission()` + `validate_can_delete()`
4. On success: `entity.delete()` + redirect
5. On fail: error message + redirect

**No separate `/delete/confirm/` URLs** — legacy confirm views are deprecated and commented out.
