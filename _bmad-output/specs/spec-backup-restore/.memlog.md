- (capability) CAP-1 Manual backup creation: institutional admin or super admin can trigger creation of a backup archive containing their scoped DB records, media files, and attachments. Success: archive contains DB export + media + manifest; institutional admin scoped to own institution, super admin system-wide or selected institution(s)
- (capability) CAP-2 Backup manifest and integrity verification: every archive includes a manifest with schema/app version, included institution(s), record counts, checksums. Success: restore of an archive with mismatched schema version, altered checksum, or corrupted contents is rejected before any data is modified
- (capability) CAP-3 Restore with automatic pre-restore safety snapshot: admin can restore from a prior backup archive; system auto-snapshots current state before applying. Success: restore completes only after preview/confirmation; a failed or cancelled restore can be reverted using the pre-restore snapshot
- (capability) CAP-4 Scoped access control for backup/restore: actions permitted per existing institutional-admin/super-admin roles, reusing institution/ app's scoping. Success: institutional admin attempting backup/restore outside their institution is denied
- (capability) CAP-5 Async execution with progress and notification: backup/restore run as background jobs so large media sets do not block the request; progress visible, notification on completion/failure. Success: a multi-GB job can be started, admin navigates away, later sees completion status without HTTP timeout
- (capability) CAP-6 Backup history and retention management: admins view list of past backups (who, when, size, scope), can download or delete, optional retention policy auto-prunes old backups. Success: backup list shows metadata; delete removes archive; enabled retention policy auto-removes backups past threshold
- (capability) CAP-7 Audit logging of backup/restore actions: every create/download/restore action recorded with acting user, timestamp, scope, consistent with existing UserActivityMiddleware/UserTrackingMixin. Success: audit log shows who created/restored a given backup and when
- (constraint) Must reuse institution/ app's existing tenant-scoping and permission model (middleware.py, context_processors.py) rather than building a parallel authorization mechanism
- (constraint) Backup archives containing PHI must never be stored under or served via a publicly-accessible static/media path; download requires authenticated, permission-checked access only
- (constraint) Backup/restore must run as background/async jobs, not synchronous request-response, given existing file size limits (2GB video, 100MB doc) multiplied across many records
- (constraint) Restore must never apply directly to production data without an automatic pre-restore snapshot and an explicit confirmation step
- (constraint) A restore archive is itself a file upload and must pass the same MIME/type/size validation as other uploads (python-magic pattern) before being trusted
- (constraint) Backup/restore trigger endpoints must be rate-limited per existing django_ratelimit pattern to prevent abuse via repeated large-job triggers
- (decision) Non-goal: real-time/continuous replication or point-in-time recovery -- this is snapshot-based backup, not an HA/replication solution
- (decision) Non-goal: cross-institution data merging during restore -- a restore applies only within the scope it was created for
- (decision) Non-goal: automatic offsite/cloud storage upload (S3/Azure) is not committed for this iteration -- captured as an open question, not a requirement
- (decision) Non-goal: backup/restore of deployment configuration (Django settings, environment secrets) is out of scope -- already covered separately by scripts/switch_env.py; this feature covers application data (DB + media/attachments) only
- (decision) Success signal: super admin triggers a full-system backup and institutional admin triggers a scoped backup of only their institution's data; both can later restore through a preview-confirm flow with automatic pre-restore snapshot; backup/restore actions appear in the audit trail -- demonstrable end-to-end on staging with production-representative media volume, no Django shell/manual DB intervention required
