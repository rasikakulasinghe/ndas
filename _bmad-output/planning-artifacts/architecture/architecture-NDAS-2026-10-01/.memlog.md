- (version) Python 3.10+ runtime (3.11 recommended in DEPLOYMENT.md); python-magic-bin is Windows/macOS-only, Linux hosts rely on system libmagic via python-magic. [ADOPTED]
- (version) Frontend stack frozen: AdminLTE 3.2 + Bootstrap 4.6 + Font Awesome 6.4 + HTMX + Video.js. CLAUDE.md explicitly forbids changing CSS framework/Bootstrap version. [ADOPTED]
- (version) No djangorestframework, no celery task runner, no channels/websockets in requirements.txt despite amqp/billiard/kombu/vine (celery's own deps) being present as apparent transitive stragglers. [ASSUMPTION: treat as unused/stray, not a hidden async layer -- flag for pruning, don't build against them]
- (version) No psycopg/psycopg2 driver pinned in requirements.txt even though settings.py supports a full postgresql DATABASES branch for production/VPS deploys. [ASSUMPTION: Postgres driver is installed out-of-band on VPS deploys, not tracked in requirements.txt -- a real production-deploy divergence risk]
- (decision) Paradigm: Django monolithic MVT. Single Django process serves business logic, data access, and server-rendered templates; HTMX supplies partial-page dynamic interaction. No separate API layer, no SPA frontend, no microservices. [ADOPTED]
- (constraint) AD-1 binds: all apps. Prevents: a future feature introducing a parallel API surface (DRF, GraphQL, a JS SPA talking JSON) that fragments the single server-rendered MVT paradigm. Rule: all dynamic UI goes through server-rendered templates + HTMX partials; JsonResponse is permitted only as an HTMX/AJAX partial-data endpoint for an existing page, never as a general-purpose external API.
- (decision) Nine domain apps, one-way dependency: ndas/custom_codes/ is the shared utility layer; domain apps (patients, users, video, reports, problemlist, backup, institution, referral) import from custom_codes, never the reverse, and custom_codes never imports a domain app. [ADOPTED]
- (constraint) AD-2 binds: all apps + ndas/custom_codes. Prevents: circular imports and shared-utility code silently forking per-app (e.g. two apps each writing their own sanitizer). Rule: cross-cutting logic (validators, sanitization, delete rules, error handling, abstract base models) lives only in ndas/custom_codes/; a domain app needing shared behavior extends/imports it rather than reimplementing it locally.
- (decision) Every persisted model (except AbstractUser-derived CustomUser) inherits from both TimeStampedModel and UserTrackingMixin from Custom_abstract_class.py, giving created_at/updated_at/added_by/last_edit_by for free. [ADOPTED]
- (constraint) AD-3 binds: all models. Prevents: one app hand-rolling its own timestamp/audit fields with different names/semantics (e.g. date_created vs created_at), breaking generic admin/reporting/delete-permission code that assumes these fields exist. Rule: class MyModel(TimeStampedModel, UserTrackingMixin) is mandatory for new models; added_by/last_edit_by are never set manually in view code.
- (decision) added_by/last_edit_by are populated automatically by UserActivityMiddleware (users/middleware.py) on every save() within a request context, not by view code. [ADOPTED]
- (constraint) AD-4 binds: all apps with user-tracked models. Prevents: divergent manual population (some views setting added_by=request.user, others forgetting, others setting it wrong on edit vs create). Rule: views never set added_by/last_edit_by directly; the middleware is the single population path.
- (decision) View stack convention: @login_required(login_url='user-login') + @require_http_methods([...]) or @require_GET + @ratelimit(key='user_or_ip', rate=...) + optionally @handle_view_errors(redirect_url=...), with get_object_or_404() mandatory instead of .objects.get(). [ADOPTED]
- (constraint) AD-5 binds: all views. Prevents: inconsistent error handling (raw 500s vs friendly redirects), missing rate limits on CRUD, and DoesNotExist leaking as an unhandled 500 instead of a 404. Rule: every view handling a single object uses get_object_or_404(); create/edit endpoints carry a 10/m ratelimit, delete endpoints 5/m; cross-cutting exceptions route through @handle_view_errors / @log_and_suppress rather than ad hoc try/except per view.
- (decision) Delete permission and business-rule logic is centralized in ndas/custom_codes/delete_helpers.py (has_delete_permission, validate_can_delete, get_entity_warning_items/get_entity_detail_items) and the universal delete_confirmation_modal.html partial. [ADOPTED]
- (constraint) AD-6 binds: all deletable entities. Prevents: each app writing its own delete-permission check and silently diverging (e.g. one app lets staff delete others' records, another doesn't; one checks GMA-reference before deleting a Video, another forgets and orphans an assessment). Rule: any new deletable entity's permission/business-rule check is added to delete_helpers.py and its template includes the shared delete modal partial -- never a bespoke per-app delete check.
- (decision) All user-supplied free text is sanitized before persistence/render via sanitize_text_input() / sanitize_html() / sanitize_plain_text() (bleach-based) in custom_codes/validators.py and sanitization.py; all user-controlled text going into an Excel export row is escaped via escape_excel_row()/escape_excel_formula() before ws.append(). [ADOPTED]
- (constraint) AD-7 binds: all apps accepting free text input or producing Excel exports. Prevents: an XSS hole from one app skipping sanitization, or a formula-injection hole (leading =,+,-,@) from an export path that forgot escape_excel_row(). Rule: no model/form field holding user free text is saved or rendered without passing through the shared sanitizer; no Excel export appends a row of user-controlled cells without the shared escaper.
- (decision) File uploads (video/image/document) are validated through one pipeline: extension allowlist, size limit from FILE_UPLOAD_LIMITS, MIME-type check via python-magic, filename sanitization via sanitize_filename() -- all in custom_codes/validators.py. [ADOPTED]
- (constraint) AD-8 binds: video, patients (attachments), institution (logos). Prevents: a new upload type (e.g. a future document category) skipping MIME verification because its own app wrote a shortcut extension-only check. Rule: any new file-upload field runs through the shared validator pipeline, not a bespoke per-app check.
- (decision) Multi-institution data scoping goes exclusively through InstitutionScopedManager.for_institution(request.institution) (institution/managers.py) on Patient and referral models; institution=None returns all rows (SUPERADMIN / legacy compatibility). InstitutionContextMiddleware attaches request.institution on every authenticated request. [ADOPTED]
- (constraint) AD-9 binds: patients, institution, referral, and any future institution-scoped model. Prevents: a view hand-filtering .filter(institution=request.institution) and missing the SUPERADMIN-sees-all / legacy-None case, silently hiding or leaking cross-institution data. Rule: institution-scoped queries always go through the manager's for_institution(); no app hand-rolls an institution filter.
- (decision) Institution-scoped file storage uses the institution-aware path generators (get_institution_video_path, get_institution_attachment_path, get_institution_logo_path) producing {institution_slug}/{category}/{filename}; Phase-1-era non-institution paths (get_video_path_file_name, get_attachment_path_file_name) remain only for pre-Phase-2 legacy records. [ADOPTED]
- (constraint) AD-10 binds: video, patients (attachments), institution. Prevents: a new institution-scoped upload type landing files outside the per-institution partition, breaking filesystem-level data isolation between institutions. Rule: any new institution-scoped FileField uses an institution-aware path generator; legacy non-partitioned generators are never used for new upload types.
- (decision) Cross-institution referrals use two independent records, ReferralSent and ReferralReceived, joined only by a shared referral_uuid -- neither has a FK to the other -- so one institution being suspended/deleted cannot cascade into the other's record. snapshot_data (JSONField) is captured once at submission and is immutable thereafter. Referral lifecycle is one-way: PENDING -> REPLIED -> CLOSED. In-app notifications are created exclusively via Django signals in referral/signals.py. [ADOPTED]
- (constraint) AD-11 binds: referral. Prevents: a convenience FK between ReferralSent and ReferralReceived that reintroduces cross-institution cascade coupling, or a notification created inline in a view that bypasses the signal path and gets missed when a second code path later triggers the same event. Rule: ReferralSent/ReferralReceived stay FK-independent (join via referral_uuid only); snapshot_data is never mutated post-creation; Notification rows are only ever created from referral/signals.py.
- (decision) Multi-step, concurrency-sensitive workflows (demonstrated by backup/restore: services.py for orchestration, job_lock.py for single-flight locking, export_stream.py, restore_validation.py/restore_preview.py/restore_apply.py/restore_audit.py as discrete pipeline stages) get a dedicated service-module layer separate from views.py, distinct from the direct view-to-model CRUD used by simple domain entities. [ADOPTED]
- (constraint) AD-12 binds: backup, and any future multi-step/transactional/background-style workflow. Prevents: a complex multi-stage operation being crammed into a single fat view function with no concurrency guard, or conversely simple CRUD being over-engineered with a needless service layer. Rule: a workflow with >1 sequential stage, a concurrency hazard, or a need for audit/rollback gets its own service module(s) plus an explicit lock (job_lock.py pattern) if concurrent invocation is possible; a single-entity CRUD stays view-direct.
- (decision) Security middleware stack order in ndas/settings.py is fixed (14 entries, +1 production-only validation middleware) and CLAUDE.md explicitly forbids reordering it. [ADOPTED]
- (constraint) AD-13 binds: ndas/settings.py MIDDLEWARE. Prevents: a new cross-cutting concern (e.g. a future audit middleware) being inserted at an arbitrary position and silently breaking a security invariant (e.g. CSRF/session/auth ordering, or security headers landing after a response is already built). Rule: new middleware is appended only at a documented, reasoned position relative to the existing 14; the existing order is never changed as a side effect of an unrelated feature.
- (decision) Tests live in a per-app tests/ package (e.g. patients/tests/test_models.py); CLAUDE.md explicitly forbids adding a top-level <app>/tests.py once a tests/ package exists, since it collides with the package and silently breaks python manage.py test project-wide discovery. Test DB is forced to a real file (test_db.sqlite3), not Django's default in-memory shared-cache sqlite, because concurrent-writer tests (e.g. backup's atomic lock test) need real SQLITE_BUSY semantics. [ADOPTED]
- (constraint) AD-14 binds: all apps' test suites. Prevents: a new app or contributor adding tests.py next to an existing tests/ package and silently breaking bare manage.py test discovery for the whole project. Rule: every app with a tests/ package keeps all test modules inside it; a top-level tests.py is never added alongside one.
- (decision) Deployment targets two shapes from one codebase: (1) cPanel/shared hosting with SQLite, Passenger WSGI, one full repo checkout per domain (demo.ndas.lk and ndas.lk each get their own app root, venv, .env, db.sqlite3 -- never share one checkout) via scripts/switch_env.py; (2) VPS/cloud with PostgreSQL for larger/high-traffic deployments. FFmpeg is a required external dependency (video metadata via moviepy/ffprobe); Redis is optional, used for prod caching/sessions when configured, LocMem/cached_db otherwise. [ADOPTED]
- (constraint) AD-15 binds: deployment/environments (both shapes). Prevents: a feature silently assuming Postgres-only behavior (e.g. a Postgres-specific query feature) that breaks the SQLite/cPanel deployment shape, or two domains on the same cPanel account sharing one checkout and clobbering each other's .env/db.sqlite3. Rule: new features stay DB-engine-agnostic (ORM-portable) unless explicitly gated by DB_ENGINE; each cPanel domain keeps its own full app root, never a shared checkout.
