# Data-Integrity Review — AD-18 / AD-19 (Date-Scoped Export & Partial Restore)

**Lens:** ad-hoc data-integrity (justified: live PK remapping + partial import against a PHI-holding medical-records DB)
**Scope:** AD-18, AD-19, and the AD-3/AD-5/AD-6 amendments they depend on. All other ADs out of scope.
**Verdict: FAIL** (one showstopper class of bug — missed FK remaps that corrupt or break every imported row — plus a second confirmed integrity hole in the identity-match logic and an unaddressed multi-institution hazard).

Grounded against: `patients/models.py`, `video/models.py`, `problemlist/models.py`, `referral/models.py`, `institution/models.py`, `ndas/custom_codes/Custom_abstract_class.py`.

---

## Finding 1 — CRITICAL: AD-19's PK remap only covers `patient`/`problem`; it misses real FKs on every cascaded model

AD-19 step 4 says: "remap any FK field that points at another object being imported in this same batch (`patient`, or `problem` via a ... map)". This is not exhaustive. Concrete counter-examples, verified in the actual models:

- **`added_by` / `last_edit_by`** — `UserTrackingMixin` (`ndas/custom_codes/Custom_abstract_class.py:30-47`) puts these two nullable `FK -> users.CustomUser` on *every* model in the cascade: `Patient`, `Video`, `Attachment`, `GMAssessment`, `HINEAssessment`, `DevelopmentalAssessment`, `Problem`, `ProblemAction`. These are never remapped and are not in the "objects being imported in this batch" set (users aren't imported at all). On `deserialize()` + save, the source-system user PK is written as-is into the target DB. Two failure modes, both bad for a PHI audit trail: (a) that PK exists in the target `CustomUser` table as an *unrelated real person* — the imported record is now silently misattributed to the wrong clinician; (b) it doesn't exist — `on_delete=SET_NULL` doesn't help here because this is an *insert*, not a delete, so the FK constraint simply fails and aborts AD-19's whole transaction, restore-wide, over a field nobody was trying to preserve fidelity on.
- **`ProblemAction.performed_by`** (`problemlist/models.py:132`) — a third, non-`problem` FK to `settings.AUTH_USER_MODEL`, nullable. Same failure mode as above, specific to this model.
- **`GMAssessment.video_file`** (`patients/models.py:863`, `OneToOneField -> video.Video`, required/non-null) — `Video` is itself remapped to a fresh PK earlier in the same dependency-ordered batch (`Video` precedes `GMAssessment` in AD-3/AD-19's own ordering). `video_file` is exactly the kind of "FK to another object being imported in this same batch" AD-19's rule is meant to catch, but it is not in the enumerated remap list (only `patient`/`problem` are named). Left unmapped, every imported `GMAssessment` either points at the *wrong* Video (if the source PK collides with an unrelated target Video row) or fails the OneToOne/FK constraint outright (aborting the transaction). This is not an edge case — it fires on the very first GMAssessment in any partial restore that includes one.
- **`GeneralPaediatricAssessment.discharged_authorized_by`** (`patients/models.py:1426`, `FK -> users.CustomUser`) — moot only because this model isn't in the cascade list at all (see Finding 3), but if it's ever added, it's a fourth instance of the same class of bug.

**Severity: Critical.** This isn't a corner case — it fires on ordinary data (any assessment tied to a video, or any record with a populated `added_by`) and either silently misattributes PHI-adjacent audit fields to the wrong user or aborts the restore transaction non-deterministically depending on target-DB PK occupancy. AD-19 must remap *every* FK on a cascaded model that targets another cascaded-and-being-imported row (`video_file`) and must explicitly decide a policy for FKs that target rows outside the import set entirely (`added_by`, `last_edit_by`, `performed_by`, `discharged_authorized_by`) — e.g., null them out on import, or map them through a superadmin-supplied "attribute unmatched authorship to this user" default, or refuse import when non-null and unmappable. Leaving them as a passthrough of source PKs is not a safe default in a system with real user tables at the target.

## Finding 2 — HIGH: identity-match logic checks only the *first* non-null identifier, so a target-DB collision on a different field goes undetected until it hits the DB constraint (or worse, silently mismatches)

AD-19 step 1: "attempt to match ... using whichever of `bht`, `nnc_no`, `ptc_no`, `pc_no` that record has populated (first non-null field wins)". All four fields are independently `unique=True, null=True` on `Patient` (`patients/models.py:156-200`) — a real patient can plausibly have more than one of these set (e.g. `bht` *and* `pc_no`).

Concrete failure: an archived patient has `bht="123"` (no match in target — `bht` "wins" as the first populated field, record is classified import-set) but also has `pc_no="XYZ"`, and the target DB already has a *different*, unrelated patient with `pc_no="XYZ"`. The match step never looks at `pc_no` because `bht` already "won." The record proceeds through AD-19 step 4 as a new import with `pk=None`, and the `save()` violates the DB's `unique=True` constraint on `pc_no` — aborting the entire single-transaction apply (per AD-19 step 4, "all-or-nothing"), taking every other legitimately-importable patient in the batch down with it. Nothing in the spine's "restore preview" (step 2) would have surfaced this ahead of time either, since the preview is built from the same first-field-wins partition.

This is exactly the gap the review brief flagged ("an imported patient's identifier value collides with an existing target patient's identifier through a field the matching logic didn't check") and it is real. **Fix:** match against *all four* populated identifiers, not just the first; treat a record whose fields point to *different* existing target patients as an explicit conflict requiring admin resolution, not a silent skip/import binary.

## Finding 3 — HIGH: institution assignment on the imported `Patient` row is unaddressed; two real completeness gaps in the cascade list inherited from AD-3

- **Institution FK not remapped.** AD-19's restore precondition is "the target institution must already exist (matched by slug), same as AD-3's full-scope restore." That sentence establishes *that* institutions aren't recreated, but never says how the *imported Patient row's own `institution_id` field* — a raw source-system PK embedded in the serialized record — gets pointed at the correct target `Institution` row. AD-3's full-scope restore gets away with leaving this field untouched only because it explicitly assumes "restore always runs against the same live system" (source and target are the same DB, so PKs already agree). AD-19's partial restore has no such guarantee — its entire premise (identity-matching against patients that may already exist under different PKs) implies the target can be a genuinely different system/point in time. A super admin's system-wide (`BackupJob.scope=null`, multi-institution) date-scoped archive makes this concrete: each archived patient's `institution` field is a source-side PK; without an explicit slug-based remap step analogous to the patient/problem PK map, an imported patient silently lands under whatever institution happens to own that raw PK number in the target DB (or the insert fails on an FK constraint if no such institution exists there). This directly matches the review brief's concern 3 ("silently inherited/assumed" rather than explicit) — confirmed as unaddressed.
- **Cascade list omits real patient-scoped models.** AD-3/AD-18/AD-19's fixed model list is `Patient, Video, Attachment, GMAssessment, HINEAssessment, DevelopmentalAssessment, Problem, ProblemAction`. Two models with a direct `patient` FK exist today and are absent from that list: `CDICRecord` (`patients/models.py:1093`) and `GeneralPaediatricAssessment` (`patients/models.py:1368`), plus `referral.ReferralSent`/`ReferralReceived` (`referral/models.py:50`, patient-FK'd, handled separately in AD-3 via its own institution-scoped manager but not folded into AD-18's patient-cascade filter or AD-19's remap batch at all). The Deferred section calls the list "hand-maintained... must be updated by hand if a *future* model gains a FK to Patient" — but `CDICRecord` and `GeneralPaediatricAssessment` are not future models, they exist now, with real clinical data (CDIC discharge tracking, GPA assessments) that a date-scoped backup silently drops and a date-scoped restore has no way to bring back. This directly undercuts AD-18's own stated purpose ("prevents ... a referentially incomplete patient") — the incompleteness just runs in the other direction (Patient present, real related clinical records absent) and isn't caught by any check described.

## Finding 4 — MEDIUM: skipped patients' media files — disposition never specified

Neither AD-19 nor the Structural Seed section says what happens to `media/{institution_slug}/videos/...` and `media/{institution_slug}/attachments/...` entries in the zip that belong to a skip-set patient (matched, therefore the owning `Video`/`Attachment` DB rows are never created). AD-13 describes media restore purely mechanically ("reads the zip entry-by-entry ... copies via chunked `shutil.copyfileobj`") with no mention of cross-checking against the DB-level skip/import partition from AD-19. Left as-is, the most natural implementation copies every media file present in the archive unconditionally, producing orphaned PHI media files on disk with no corresponding `Video`/`Attachment` row (wasted storage at minimum; an un-owned, un-auditable PHI file at worst, permanently outside the app's access-control views since nothing points at it). The spine needs an explicit rule: media copy for date-scoped restore must be filtered to only the import-set patients' files, mirroring the DB-level skip decision.

## Finding 5 — LOW/NOTE: checksum-before-apply ordering is preserved but not explicitly re-stated for the single-file case

AD-6's "verify the zip hash against `BackupJob.archive_checksum`, then verify each per-file checksum from `manifest.json` before applying that file's contents" is unchanged text and mechanically still applies to `db_export.json` as one file (one checksum, one atomic "apply" unit — which happens to line up naturally with AD-19's own single-transaction apply step). There's no actual contradiction with AD-13's no-full-buffering rule either: hashing can be done via a first streaming pass, deserialization via a second. This is fine as designed, but AD-19's text never cross-references AD-6's checksum gate explicitly when describing the new partial-restore code path (steps 1–4 read as if they start directly from "read the `patients.patient` array"). Since this is new code (not a reuse of AD-3's existing restore path), an implementer skimming AD-19 alone could plausibly start parsing/matching before the checksum check runs. Recommend AD-19 add one sentence: "steps 1–4 run only after AD-6's zip-hash and `db_export.json` checksum validation succeed." Documentation clarity issue, not a design flaw.

## Non-findings (checked, no issue)

- `HINEAssessment` and `DevelopmentalAssessment` have only the `patient` FK (plus the universal `added_by`/`last_edit_by` covered in Finding 1) — no other hidden FKs.
- `Problem` → `ProblemAction` dependency ordering (`Problem` before `ProblemAction` in AD-3/AD-19's fixed order) is correct and sufficient for building the Problem source-PK→new-PK map before `ProblemAction` rows are processed — assuming Finding 1's `performed_by` gap is also closed.
- The four identifier fields (`bht`, `nnc_no`, `ptc_no`, `pc_no`) are confirmed `unique=True, null=True` on `Patient` exactly as AD-19 assumes.
- `Institution.slug` is confirmed `unique=True` and immutable post-creation, so "matched by slug" is a sound target-institution lookup key *if* it were actually applied to the imported Patient row's institution FK (see Finding 3).

## Recommendation

Do not proceed to implementation on AD-19 as written. At minimum:
1. Enumerate and remap *every* FK on a cascaded model, not just `patient`/`problem` — explicitly including `video_file` (batch-internal) and defining a policy for `added_by`/`last_edit_by`/`performed_by`/`discharged_authorized_by` (batch-external, user-referencing).
2. Match candidate identity across all four populated identifier fields, not first-populated-wins; treat cross-field conflicts as a blocking case surfaced to the admin, not a silent partition.
3. Add an explicit `institution` remap (slug-based, same mechanism as the Patient/Problem PK map) for every imported Patient row, and resolve whether `CDICRecord`, `GeneralPaediatricAssessment`, and the `referral` models belong in AD-18/AD-19's cascade.
4. Specify that media-file restoration for a date-scoped archive is filtered to the import-set, matching the DB-level skip decision.
5. Add one explicit sentence tying AD-19's apply steps to AD-6's pre-apply checksum gate.
